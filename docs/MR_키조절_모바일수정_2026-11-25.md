# MR 실시간 키 조절 — 모바일에서 "이 브라우저에서는 키 조절을 쓸 수 없습니다" 수정 (2026-11-25, v22)

## 1. 주성 님이 보신 증상

- 안드로이드 크롬(인앱 브라우저·커스텀탭 포함)에서 `https://xorrus464-stack.github.io/strum-busking-test/`의
  MP3 MR을 재생하고 미니 플레이어의 `− / +`를 누르면
  **"이 브라우저에서는 키 조절을 쓸 수 없습니다. 원음으로 재생합니다."** 토스트가 뜨고,
  라벨이 `0키`로 되돌아갔습니다(2026-11-25 06:19 KST 캡처: 「생각을 멈추다 보면」 MR 0:09/3:16 재생 중).
- 재생되는 음원 자체는 이미 남자키(-5반음) MP3라 소리는 정상이었고, **실시간 키 조절기만 죽어 있었습니다.**

## 2. 원인 (두 가지가 겹쳐 있었음)

### (1) v21 워클릿의 치명적 버그 — 키를 눌러도 소리(피치)가 바뀌지 않았음

`src/pitch-worklet.js`는 실제 피치 비율을 `this.ratio`로 읽고 있었는데, 이 값은
`port.postMessage({type:'ratio'})`로만 바뀌었습니다. 그런데 `app.js`는

```js
g.node.parameters.get('ratio').value = ratio;   // AudioParam 만 바꿈 (port 메시지 없음)
```

처럼 **AudioParam만** 바꾸고 있었습니다. 결과:

- `this.ratio`는 1로 고정 → 읽기 헤드가 원속도로 돌아 **피치는 그대로**.
- `dry` 판정만 AudioParam 값(`target`)을 봐서 `wet` 경로로 들어감 → 90ms 입자의 절반(45ms)만큼
  지연된 0키 소리를 냄. 라벨은 `+2키`로 바뀌는데 소리는 그대로인 상태였습니다.
- 실측(수정 전 v21, 440Hz 사인 테스트): `+2키` 라벨에서 출력 438.7Hz = **피치 변화 없음**.

### (2) `ensurePitch` 가 모바일에서 `null`을 반환 — AudioWorklet 실패 시 대안이 없었음

```js
ctx = new AC();
await ctx.audioWorklet.addModule('src/pitch-worklet.js?v=21');   // ← 여기서 실패하면 끝
src = ctx.createMediaElementSource(audioEl);
```

- 안드로이드 **WebView 기반 인앱 브라우저**(카카오톡·인스타그램 등)나 일부 커스텀탭에서는
  `AudioWorklet`/`addModule`이 없거나 막혀 있어 이 단계에서 예외가 나고, catch에서
  `pitchGraph=null` → **키 조절 전체가 포기**되었습니다.
- 게다가 `teardownPitch()`가 `ctx.close()`로 컨텍스트를 닫고, 다음 호출에서 같은 `<audio>` 요소에
  `createMediaElementSource`를 **다시** 걸다가 `InvalidStateError`가 나는 경로도 있었습니다
  (미니 플레이어를 닫았다 열거나, 리렌더로 요소가 바뀌는 경우).
- 예전 catch 블록은 `src.connect((ctx||new AC()).destination)`처럼 정리도 어중간했습니다.

## 3. 고친 내용 (v22)

| 파일 | 변경 |
|---|---|
| `src/pitch-grain.js` (신규) | 그래뉼러 피치 시프트 **핵심 알고리즘을 한 곳으로** 분리. AudioWorklet과 ScriptProcessor가 같은 코드를 씀. `GrainShifter.process(input, output, frames, ratio)` · `createScriptPitchNode(ctx)` |
| `src/pitch-worklet.js` | `import './pitch-grain.js?v=22'` 후 얇은 래퍼만 유지. **`target`(= AudioParam `ratio`)을 그대로 실제 비율로 사용**. port `ratio` 메시지는 호환용 override로만 |
| `src/app.js` | ① AudioContext **앱 전체 1개** 재사용 ② `<audio>` 요소별 그래프를 `WeakMap`에 보관(중복 `createMediaElementSource` 방지) ③ AudioWorklet 실패 시 **`createScriptProcessor(2048,2,2)` 자동 폴백**(같은 알고리즘) ④ 비율은 AudioParam + port 양쪽에 설정 ⑤ 닫을 때 컨텍스트를 close하지 않고 원음 경로로 되돌린 뒤 `suspend` |
| `src/styles.css` | 안내 토스트에 `pointer-events:none` — 토스트가 떠 있는 3.5초 동안 아래 `−/+` 버튼 탭이 먹히지 않던 문제 제거 |
| `index.html`·`sw.js` | 캐시 버전 `v21 → v22` (styles/app/seed 쿼리, `strum-busking-test-v22`) |

동작 경로는 이제 3단계입니다.

1. **AudioWorklet** (지원하면 가장 음질이 좋음)
2. **ScriptProcessor 폴백** (WebView·커스텀탭·구형 브라우저) — 같은 그래뉼러 알고리즘
3. 둘 다 불가 → 지금처럼 원음 재생 + 안내 토스트(단, 이 경우만 토스트가 뜸)

## 4. 검증

### 새 테스트: `python3 tools/mr_key_audio_test.py`

기존 `tools/mr_key_ui_test.py`는 라벨·토스트만 봐서 (1)번 버그를 통과시켰습니다.
새 테스트는 **실제 소리를 잰다**:

- 로컬 HTTP 서버가 440Hz 사인 WAV(`/__test/tone.wav`)를 만들어 주고, 미니 플레이어의 `<audio>`를
  그 톤으로 바꾼 뒤 앱이 만든 그래프 출력을 `AnalyserNode`(fftSize 16384)로 떠서 최고점 주파수를 읽습니다.
- `+2반음` → 493.9Hz(2^(2/12)), `0키` → 440Hz, `-5반음` → 329.6Hz(2^(-5/12))인지 확인.
- `AudioWorklet.prototype.addModule`을 거부시켜 **안드로이드 WebView를 재현**하고, 같은 피치 이동이
  되는지 + 그래프가 `ScriptProcessorNode`인지 확인.
- 워클릿·ScriptProcessor를 **둘 다** 막으면 안내 토스트 1회·`0키` 복귀·페이지 오류 0인지 확인.
- 미니 플레이어를 닫았다 다시 열어도(새 `<audio>` 요소) 키 조절이 계속 되는지 확인.

결과(2026-11-25, Chromium · PC 1280×900 · 갤럭시 412×915 에뮬레이션):

```
RESULT PASS (76/76)
```

주요 수치:

| 환경 | 경로 | 440Hz | +2반음 | -5반음 |
|---|---|---|---|---|
| PC | AudioWorkletNode | 438.7Hz | **495.3Hz** | **328.4Hz** |
| 갤럭시 | AudioWorkletNode | 438.7Hz | **495.3Hz** | **328.4Hz** |
| PC | ScriptProcessorNode(폴백) | 438.7Hz | **495.3Hz** | **328.4Hz** |
| 갤럭시 | ScriptProcessorNode(폴백) | 438.7Hz | **495.3Hz** | **328.4Hz** |

(측정 해상도는 16384 FFT · 44.1kHz에서 2.7Hz/bin 이라 438.7/495.3/328.4는 440/493.9/329.6과 같은 값으로 봅니다.)

## 5. 남은 확인

- 주성 님 실제 기기(인앱 브라우저)에서의 최종 확인은 배포 후 그 기기에서 `− / +`를 눌러 봐야 합니다.
  이제 `addModule`이 막혀 있어도 ScriptProcessor 폴백으로 동작해야 합니다.
- 그 브라우저가 **`createMediaElementSource` 자체를 막는** 극단적인 환경이라면 여전히 안내 토스트가 뜹니다
  (이 경우는 WebAudio 그래프를 만들 수 없어 실시간 키 조절이 원천적으로 불가능 — 그때는 곡별 MP3를
  반음별로 미리 만들어 두는 방식이 필요합니다).
